## 0. 使用规则

本文档不是愿景清单，而是后续制作任务的执行边界。

任何 worker 开始工作前，主 Agent 必须明确提供：

1. 完整上下文；
2. 允许访问和修改的文件范围；
3. 明确的任务边界和非目标；
4. 预期输出；
5. 可执行的验收标准；
6. 所需的验证命令；
7. 是否允许继续派生子代理。

worker 不得自行改变主任务目标，不得把相邻需求加入当前任务，也不得以“顺手优化”为理由扩大修改范围。

主 Agent 负责：

- 版本拆解；
- 任务派发；
- 依赖协调；
- 结果验收；
- 版本号和发布决策；
- 回滚判断。

`luna_worker` 负责：

- 执行范围明确、可以独立完成的子任务；
- 按任务契约修改或检查指定资源；
- 返回可复核的证据；
- 发现边界冲突时停止扩展并报告。

表情范围：

- `shy`；
- `serious`；
- `surprised`；

### 4.3 视觉验收标准

CG 和背景：

- 至少 `1600×900`；
- 画面比例 `16:9 ±1%`；
- 单张不超过 `500 KiB`；
- 无文字水印；
- 无明显错误手部；
- 角色身份可辨认；
- 手机中央裁切不遮挡关键主体；
- 底部 30% 保留对白安全区。

表情立绘：

- 至少 `800×1600`；
- 竖版；
- 单张不超过 `300 KiB`；
- 服装、发色、脸部锚点与既有立绘一致；
- 表情切换时位置和比例不跳变。

### 4.4 素材接入规则

只有在素材实际存在并通过尺寸检查后，才允许把 `visualAssets.ts` 中对应项从 `pending` 改为 `ready`。

禁止：

- 复制旧图冒充新图；
- 用空图或拉伸图占位；
- 直接删除回退图；
- 修改审计脚本来绕过正式发布检查；
- 把候选 PNG 自动视为正式成品。

### 4.5 1.8 正式发布闸门

必须全部通过：

```text
npm run audit:assets:final
npm run typecheck
npm test
npm run build
npm run test:e2e
```

并额外检查：

- 36 个资源全部为 `ready`；
- 36 个资源全部进入离线缓存清单；
- 12 条告白路线均可触发对应 CG；
- 图鉴路径和剧情路径一致；
- 375×812、430×932、横屏和桌面均无遮挡；
- 断网重进后正式素材可读取。

### 4.6 当前阻塞

当前环境没有可用的内置图像生成工具。

因此在用户提供素材或明确授权 CLI/API 生图路径前，worker 只能：

- 审计提示词和路径映射；
- 检查现有回退链路；
- 生成接入清单；
- 编写验收脚本和测试。

worker 不得自行把回退素材改为正式素材。

## 6. 2.0 章节回看与二周目（历史方案，已归档）

> 本节保留当时的方案比较记录，不再作为实施授权。当前决策是 `SOL-PLAN-2.0-3.0.md` 中的“类型化标准检查点 + 通用隔离回放会话”。

### 6.1 已完成基础

当前已经实现：

- 历史记录显示所属剧情幕；
- 历史记录按剧情幕筛选；
- 关键选择显示非剧透分岔提示。

这些功能不改变存档结构，也不把终局状态当成章节起点。

### 6.2 尚未完成

- 真正的章节入口；
- 章节起点状态；
- 路线状态重建；
- 回放期间的存档隔离；
- 回放退出后的精确恢复；
- 旧存档兼容；
- 章节重玩端到端测试。

### 6.3 章节重玩方案

#### 方案 A：预制章节检查点

为每条路线和每个章节维护固定初始状态模板。

优点：

- 成本较低；
- 容易测试；
- 不必大改历史结构；
- 回滚简单。

缺点：

- 需要维护多份模板；
- 新增状态字段时需要同步模板。

#### 方案 B：根据玩家历史重建状态

在历史记录中保存稳定的选择 ID，从初始状态重新执行到目标章节。

优点：

- 状态最准确；
- 长期维护性更好；
- 更适合真正二周目。

缺点：

- 需要扩展 `HistoryEntry`；
- 需要存档迁移；
- 旧存档没有选择 ID 时需要兼容；
- 实现和测试成本最高。

#### 方案 C：只做章节文本回顾

章节选择只过滤和展示历史文本，不重新执行选项。

优点：

- 风险最低；
- 不改变存档；
- 可以快速发布。

缺点：

- 不是真正重玩；
- 无法重新体验分支；
- 只能算回顾功能。

### 6.4 推荐顺序

推荐：

1. 先保留当前方案 C 的历史回顾能力；
2. 再实现方案 A 的隔离章节回放；
3. 后续如果需要更高精度，再评估方案 B。

不建议在当前阶段直接实现方案 B，因为项目尚未拥有完整的选择 ID 历史合同。

### 6.5 2.0 验收标准

如果选择方案 A，必须满足：

- 每条组织路线的每个可回放章节都有明确起点；
- 回放状态与正常游玩状态分离；
- 回放不写入自动存档；
- 回放不写入快速存档；
- 回放不改变当前关系值；
- 回放不改变收藏；
- 回放不改变结局解锁；
- 回放退出后恢复进入前节点和状态；
- 手机、桌面和键盘操作均可用；
- 旧存档继续可读。

## 8. luna_worker 派发协议

### 8.1 任务描述模板

每次派发必须包含：

```text
任务目标：

当前上下文：

允许读取的范围：

允许修改的文件：

明确不允许修改的文件：

任务边界：

预期输出：

验收标准：

必须运行的验证：

是否允许派生子代理：否
```

### 8.2 只读任务

只读任务可以并行，适合：

- 版本和发布审计；
- 关系剧情图审计；
- 资产路径审计；
- 测试覆盖盘点；
- 2.0 架构方案比较。

只读 worker 不得为了“方便验证”修改文件。

### 8.3 写入任务

当前没有确认可用的独立 worktree，因此写入任务必须串行。

写入 worker 必须：

- 只修改任务清单中的文件；
- 保留已有用户修改；
- 不覆盖其他 worker 的改动；
- 不顺手重构；
- 完成后返回 diff 摘要和测试证据。

### 8.4 worker 返回格式

每个 worker 至少返回：

1. 完成了什么；
2. 检查或修改了哪些文件；
3. 运行了哪些命令；
4. 每项验收标准是否满足；
5. 未验证事项；
6. 阻塞、风险和建议；
7. 是否发现超出任务边界的需求。

## 10. 主 Agent 验收流程

每个 worker 完成后，主 Agent 必须：

1. 检查实际修改文件；
2. 对照任务允许范围；
3. 检查是否顺手改动无关内容；
4. 运行对应验证命令；
5. 按验收标准逐项核对；
6. 区分已验证、未验证和失败项；
7. 未达标时重新派发；
8. 不以“测试通过”替代范围验收。

如果多个 worker 无法并行，必须先检查：

```text
~/.codex/config.toml
```

确认：

```text
agents.max_concurrent_threads_per_session
```

没有被设置为 `1`。

但即使并发配置允许，多写入任务在没有独立 worktree 时仍必须串行。
