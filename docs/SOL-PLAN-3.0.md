## 1. 目标与范围

3.0 把已经完整可玩的双季客户端从候选状态晋升为稳定版，并形成第三季以后可消费的不可变第二季结果。它不是“最后补一批剧情”的缓冲区；任何新场景、路线、结局或选择必须在 2.9 前完成，或进入经批准的 3.1 补遗范围。

玩家侧交付：在一个客户端内完整游玩第一季、第一季补遗和第二季；选择第一季结果开启第二季，完成全部主要结局、失败状态、路线尾声和关系收束。

## 2. 必要前置

- 2.9 全部 episode、主要结局、尾声和连续性矩阵完成；
- 第二季 payoff ledger 中所有必需项已回收或获批关闭；
- 所有正式节点、选择、结局和素材 ID 冻结；
- `targetRelease <= 3.0` 的托管视觉全部 ready；
- schema1–4 → schema5、旧收藏 → v2 的迁移矩阵通过；
- `3.0.0-rc.N` 在独立预发布环境通过；
- P0/P1 为零，P2 均有明确决定。

## 3. 第三季交接产物

3.0 完成第二季时必须能够生成并保存不可变 `Season2OutcomeRecord`：

```text
outcomeId
outcomeRecordVersion
lineageId
parentOutcomeIds
seasonId = season2
contentRevision
endingId
relationshipResolutionId
durableFacts
payloadDigest
createdAt
```

该记录通过 `parentOutcomeIds` 指向实际使用的第一季结果，并写入独立 outcome archive；它不占用 auto/quick/手动存档槽，也不包含完整历史或任意 flags。删除普通第二季存档不会删除结果记录；删除结果记录必须单独确认影响。

3.0 acceptance 必须验证 outcome archive 的创建、去重、导出、导入、损坏隔离、普通存档删除隔离和回滚。未完成这项交接，3.1 可以做只读复盘，但不能开始第三季开局实现。

## 4. 冻结规则

3.0 阶段允许：

- 修复崩溃、错档、断链、事实错误、缺图、离线和无障碍问题；
- 补测试、迁移夹具、发布说明、部署和回滚证据；
- 在不改变含义和构图意图的前提下修正文案或压缩资产。

3.0 阶段禁止：

- 新增或扩写剧情；
- 新增路线、角色、结局、系统或提示词项；
- 改写已发布选择含义；
- 为第三季提前塞入未确认字段；
- 删除旧数据键、失败测试或降低资产门禁。

## 5. 最终验收矩阵

### 5.3 客户端、离线与素材

## 8. 发布与回滚

1. 在独立预发布地址部署不可变 RC。
2. 使用复制的真实 v4/v5 数据记录迁移前后键和哈希。
3. 完成内容、数据、设备、离线、素材和 outcome archive 矩阵。
4. 把 `current` 指回最后稳定 2.x，确认旧内容可用且 v5/archive 未被覆盖。
5. 再切回 RC，确认第二季进度和归档结果恢复。
6. 发布最终不可变 `v3.0.0` 并做公网烟测。
7. 任一步失败生成新 RC，不覆盖旧候选。

## 9. 3.0 后复盘闸门

3.1 开始前形成真实的 `S2-POSTMORTEM.md`，区分：

- 玩家或人工走查发现的叙事缺口；
- 2.9 明确移入 3.x 的可选线索；
- 只需修错、不应扩写的内容；
- 已完整关闭、不应重复消费的结局；
- 第三季可能使用但尚未获批的连续性维度。

没有证据支持的“感觉应该再写一点”不能成为 3.1 范围。

## 10. 完成标准

P0/P1 为零；P2 有明确决定；自动、人工、离线和公网矩阵通过；全部图片由用户确认；迁移、outcome archive 和回滚证据完整；release、acceptance、rollback 与实际构建一致。满足后 3.0 才能作为 3.1–4.0 的真实基线。

## 11. 兼容性妥协

- 回滚到只支持早期 v5 的版本时，第三季交接字段或 archive UI 可能不可见，但数据保留。
- 第一季旧历史无法转换成完整选择日志，多季结果仍只继承可证明摘要。
- outcome archive 增加少量本地数据和导出体积，换取普通来源档不长期占槽。

## 12. 有意不做

- 不新增第二季剧情、图片需求、系统功能或未经评审的 schema 字段。
- 不创建第三季正式节点或具体提示词。
- 不删除 v4/v3/legacy 存档、旧收藏或 outcome 旧记录。
- 不假设第三季必然立项；3.1–4.0 仍需以真实 3.0 复盘为前提。
