# 《4945区》2.0 → 3.0 Sol 总方案

> 文档状态：已按“内容主导、逐集交付”重写；这是 2.0–3.0 的权威规划索引，不代表已授权实现。
>
> 重写日期：2026-08-05。
>
> 事实边界：当前第一季只确认到 2026-07-28；第二季的具体日期、事件、角色去留、路线和结局均须由用户另行冻结。
>
> 分工边界：Sol 负责规划、剧情合同、提示词和验收；图片由用户使用外部模型生成；后续代码与内容落盘须另行授权。

## 0. 结论

2.0–3.0 不再采用“2.1–2.6 只做技术、2.7 试切片、2.8 一次性补完全部剧情”的安排。冻结后的版本模型是：

- `2.0` 收口当前已实现的第一季章节回放候选，不临时追加剧情；
- `2.1` 先补第一季组织与成员叙事缺口；
- `2.2` 以完整可玩的第二季共通序章开启第二季，并同时启用生产 schema5；
- `2.3–2.9` 按同一时间线切片推进所有活跃路线，每个小版本都交付一个有开端、冲突、选择、后果和阶段收束的剧情单元；
- `3.0` 不再突击新增剧情，而是把已经完整交付的第二季晋升为稳定完整季。

技术能力不再单独占用多个无内容版本。按季模块、存档迁移、离线分包、选择回收和资产管理都作为对应剧情版本的支撑范围随片交付。

## 1. 本次重写解决的问题

| 问题 | 风险 | 冻结处理 |
|---|---|---|
| 2.1–2.6 几乎没有可玩剧情 | 玩家连续多个版本感知不到内容进展 | 2.1–2.9 每版均有完整剧情单元 |
| 几乎全部第二季内容压在 2.8 | 写作、接入、测试和素材同时爆量 | 按时间顺序拆成序章、发展、分歧、后果、危机、高潮和尾声 |
| 先按路线做完、再拼时间线 | 共享事件漂移，部分路线长期无更新 | 每版横切全部活跃路线，不按路线纵向开发 |
| schema5 推迟到第二季剧情之后 | 预览存档、生产存档和内容节点需要二次迁移 | 2.2 首个稳定第二季版本即使用 canonical schema5 |
| schema 版本与剧情修订混为一谈 | 文字修订也可能触发错误迁移 | `schemaVersion` 与 `contentRevision` 分离 |
| 第一季继承直接依赖零散 flags | 第二季形成不可维护的隐式 API | 只读取版本化 outcome record 与结果白名单 |
| 旧历史最多 500 条且没有稳定选择 ID | 无法完整带入第一季过程，也不能精确重演旧选择 | 保留 v4 第一季档；第二季建立新历史，不伪造旧选择 |
| 选择只有即时效果，延迟回收没有总账 | 后期容易遗漏承诺、出现伪分支 | 建立 choice payoff ledger，并按版本验收 |
| 路线内容以节点数量追求“平均” | 会补出机械、低价值内容 | 以戏剧功能覆盖和因果完整性衡量，不强求节点数相等 |
| 关系内容接近内容图的一半 | 继续平均加恋爱内容会挤压组织主线 | 2.1 优先补组织、成员和治理因果；关系只在主冲突需要时进入 |
| 图片清单只有 `pending/ready`，没有版本归属 | 缺图会无限悬空，无法判断阻断哪个版本 | 每项增加 `targetRelease` 与处置状态；每版独立提示词包和门禁 |
| 本地版本与公开状态口径冲突 | 容易把源码候选误报为线上发布 | 分开记录“线上已验证版本”和“本地实现候选” |
| 没有遥测或后端 | 无法用自动数据判断路线失衡 | 使用版本化人工走查、反馈表和选择回收审计，不虚构数据 |

## 2. 已验证基线

### 2.1 版本状态

- `game/package.json`、`GAME_APP_VERSION` 和标题页发布说明均为 `2.0.0`。
- 31 个标准章节检查点、章节选择界面和通用隔离回放内核已经存在。
- `game/deploy/RELEASE-v2.0.0.md` 已存在，但尚无独立 `game/docs/V2.0-ACCEPTANCE.md`。
- `game/public/sw.js` 仍使用 `4945-v1.7.1-r1` 缓存键。
- 两份旧路线图仍把线上稳定基线写为 `1.7.1`。

因此当前结论只能是：**2.0 是已通过主要本地验证的实现候选，不是已被本工作区证据证明的公开稳定版本。** 2.0 收口必须先统一版本、缓存、验收和发布证据。

### 2.2 当前内容构成

当前内容图共 766 个节点：

| 内容层 | 节点数 | 观察 |
|---|---:|---|
| 共通序章 | 46 | 第一季公共入口 |
| 五条组织路线 | 347 | 二组 108、三组 62、四组 62、五组 49、六组 66 |
| 第一阶段关系内容 | 120 | 多角色关系展开 |
| 关系续篇 | 252 | 已成为内容图的重要主体 |
| 制作人员页 | 1 | 第一季终点 |

路线节点数只用于发现异常，不作为配额。2.1 的优先级是补足“关键事件为何发生、成员为何行动、玩家决定如何改变局面”的组织因果缺口，而不是把五条路线机械补到相同长度，也不是继续平均增加关系日常。

### 2.3 数据与素材

- 当前稳定存档合同仍是 schema4 / `4945-vn:v4:save:*`。
- `HistoryEntry` 不保证稳定 `choiceId`，且历史上限为 500 条。
- 收藏仍使用未版本化的 `4945-vn:collection`。
- 普通资产审计可通过；当前正式源图片引用有效。
- v1.8 托管视觉为 `4/36 ready`，另有 32 项 `pending`；最终资产审计应继续失败。

当前 32 项待生成视觉不阻断 2.0 回放候选，因为 2.0 明确使用有效回退，但它们必须在下一次发布规划前被标记为“指定未来版本”“明确延期”或“取消”，不能继续作为无归属的 pending。

### 2.4 最近验证证据

- 类型检查通过。
- 27 个测试文件、303 项单元测试通过。
- 普通资产审计通过。
- 最终资产审计因 32 项待生成视觉失败，符合当前清单状态。

以上证明源码候选的本地质量，不替代浏览器端到端、真实离线更新、公网发布和人工剧情验收。

## 3. 跨版本剧情合同

### 3.1 完整剧情单元

除 2.0 收口和 3.0 晋升外，每个小版本必须交付一个可独立完成的剧情单元，至少包含：

1. 明确的时间窗口和本集局部问题；
2. 所有玩家都会经历的共通主干；
3. 冻结规格中全部活跃路线在该时间窗口内的变体；
4. 至少一个推动人物关系或组织关系变化的角色拍点；
5. 至少一个有可见即时后果的有效选择；
6. 需要延迟回收的选择登记项；
7. 对本集局部问题的阶段收束，以及指向下一集的自然钩子；
8. 本集图片提示词、素材清单、内容图测试和人工验收脚本。

“完成一段架构”“显示待续”“只有一个不可操作的预告场景”均不算完整剧情单元。集末可以保留悬念，但必须先回答本集提出的局部问题。

### 3.2 按时间切片，不按路线排队

第二季采用横向时间切片：

```text
同一时间窗口
  -> 共通事件
  -> 路线 A / B / C ... 的同期变体
  -> 关系与成员拍点
  -> 选择后果
  -> 本集完成标记
```

任何活跃路线都不能因为“尚未轮到该路线开发”而在已发布时间窗口中缺席。共享场景只维护一份，路线差异由显式条件和变体节点表达。

### 3.3 戏剧覆盖，不按节点数平均

每条活跃路线用以下覆盖矩阵验收：处境、欲望、阻力、成员立场、玩家能动性、不可逆代价、关系压力、危机、高潮、余波。节点数量可以不同，但不能缺失该时间窗口应承担的戏剧功能。

### 3.4 事实治理

每张第二季场景卡必须标注：

- `confirmed`：由用户提供并确认的事实；
- `adapted`：基于已确认事实进行合并、压缩或视角改写；
- `fictional`：明确的架空创作，不声称为真实记录。

2026-07-28 之后的任何日期、事件、人物行为和组织变化，在用户确认前都只能保留为待决槽位，不能写成正式剧情事实。具体第二季名称、日期、路线数和结局数不在本方案中猜测。

### 3.5 稳定 ID 与修订

- 第一季现有节点、结局、CG 和角色 ID 保持不变。
- 第一季补遗节点使用 `s1x-`，对应提示词使用 `S1X-`。
- 第二季节点、选择、结局和素材引用使用 `s2-`，提示词使用 `S2-`。
- 已发布 ID 只追加、不复用、不改变含义。
- 必须修正结构时，为旧节点保留 alias 或 tombstone，使旧存档能落到可解释的安全位置。
- `schemaVersion` 只表示数据结构；`contentRevision` 表示剧情图修订；文字修订不得伪装成 schema 升级。

### 3.6 选择回收总账

从 2.2 起，每个稳定选择都必须登记：

```text
choiceId
introducedIn
immediateEffect
deferredPayoffIn
routeScope
inheritanceVariantClass
fallback
testIds
status
```

`deferredPayoffIn` 可以是后续版本，但必须有明确目标。若剧情改动导致无法回收，必须提供等价回收或经用户批准关闭，不得静默遗忘。

### 3.7 继承变体分级

第一季结果只通过白名单摘要进入第二季，并按影响范围分为：

- `flavor`：称呼、回忆或一句反应，不改变场景结构；
- `scene`：替换或新增局部场景；
- `structural`：改变一段可玩路径；
- `ending`：参与结局判定。

每个继承字段必须声明最高影响级别。未经批准不得把 flavor 字段升级为结构分支，也不得为所有字段做笛卡尔积组合。

## 5. 第二季开局与存档合同

### 5.1 schema5 必须在 2.2 成为 canonical

如果 2.2 开始提供稳定第二季剧情，正式数据不能继续写临时 preview 键。2.2 必须同时完成：

- `GameState.seasonId`；
- `GameState.contentRevision`；
- 稳定 `campaignId` 与 `lineageId`；
- 新记录的稳定 `choiceId`；
- 版本化 `Season1OutcomeSummary`；
- 通用 `SeasonOutcomeRecord` / `ContinuityProfile` 基础合同；
- 第二季 episode completion；
- 收藏 v2；
- v4 → v5 的幂等迁移和回滚读取。

2.1 继续使用 schema4；2.2 起稳定客户端写 `4945-vn:v5:save:*`、`4945-vn:v2:collection` 和独立版本化 outcome archive（规划键为 `4945-vn:v1:outcomes`）。所有 v4、v3 和 legacy 键保留为只读回滚检查点，3.0 前不删除。

### 5.2 来源档与目标档

开始第二季时必须：

1. 扫描所有合法的第一季完成档；
2. 由玩家显式选择一个来源，或使用经批准的回顾建档；
3. 显示人类可读的第一季结果摘要；
4. 创建或复用不可变 `Season1OutcomeRecord`，生成稳定 lineage；
5. 由玩家选择第二季目标槽；
6. 在 v5 命名空间创建新的 season2 campaign。

此流程不得覆盖来源 v4 键。若目标 v5 槽已有进度，必须单独确认覆盖。来源槽后来变化，也不能改变已经保存到 v5 的结果摘要快照。

### 5.3 第一季结果摘要与 outcome record

摘要只包含第二季实际消费的字段：来源槽与保存时间、第一季路线、组织结果、唯一伴侣或明确的无伴侣状态、分级关系结果，以及经过登记的 durable facts。不得复制任意 flags、variables、processedNodes 或完整关系数值。

每个字段都必须有提取测试、回顾建档合法组合、第二季消费点和未匹配 fallback。未被剧情使用的字段从摘要中删除。

确认摘要时创建不可变 `Season1OutcomeRecord`，记录稳定 `outcomeId`、`lineageId`、来源、内容修订和 payload digest。普通 v4 来源档后来被覆盖或删除，不影响该记录与已创建的 season2 campaign；记录不得包含完整历史或任意 flags。

### 5.4 历史与回放

第二季建立独立、带 season/episode 标签的历史，不把第一季最多 500 条的原始历史复制进新档。第一季过程继续通过保留的 v4 存档和章节回放查看；摘要只承诺结果继承，不承诺逐选择复原。

### 5.5 多季前向兼容

schema5 从 2.2 起把结果继承设计为可扩展的 outcome/profile 合同，而不是只能保存一个固定的第一季字段块。2.9 完成第二季后追加 `Season2OutcomeRecord`；未来第三季从 outcome archive 创建新 campaign，不要求第二季来源普通存档永久占用槽位。该前向兼容不授权提前实现第三季内容。

## 6. Episode 数据合同

从 2.2 起，每个可发布剧情单元登记为 `SeasonEpisodeDefinition`：

```text
id
seasonId
release
contentRevision
chronologicalWindow
entryNodeIds
completionNodeIds
activeRoutes
consumedOutcomeFields
introducedChoiceIds
payoffChoiceIds
assetIds
validate()
```

运行时需要季/集中心展示已完成、当前可玩和未开放状态。episode completion 是显式字段，不能通过“见过某个文本节点”猜测。普通 `next` 不跨季；跨季只允许通过季协调器创建或读取目标进度。

## 7. 素材与提示词合同

### 7.1 每版交付

每个含剧情的小版本必须同步交付：

```text
<release>-ASSET-MANIFEST.md
<release>-IMAGE-PROMPTS.md
<release>-ASSET-ACCEPTANCE.md
```

每个视觉项至少记录 `assetId`、`promptId`、关联节点、类型、角色锚点、场景与情绪、构图、移动端焦点、对白安全区、负面约束、正式路径、fallback、`targetRelease`、状态和人工验收项。

### 7.2 状态规则

- `pending` 只表示“已指定未来版本且正在等待用户提供”，必须同时拥有 `targetRelease`。
- `deferred` 必须写明延期目标或重新决策日期，不阻断当前版本。
- `cancelled` 保留编号与原因，不允许复用 ID。
- `ready` 需要文件审计和人工身份、手部、文字水印、构图验收双通过。
- 稳定发布时，`targetRelease` 等于该版本的全部托管视觉必须 `ready`；不能用 fallback 冒充正式图。

图片仍由用户在外部模型生成。Sol 只根据已冻结场景写提示词，不在场景尚未确认时虚构角色动作；后续执行者只接入用户提供且验收通过的图片。

## 8. 每版验收

### 8.1 内容

- 共通主干和全部活跃路线从合法入口到本集完成节点均可达；
- 没有死节点、伪结局、越过未发布 episode 的跳转或未登记选择；
- 每个关键选择有即时后果，延迟后果进入 payoff ledger；
- 每条路线完成本集戏剧功能，而不是机械满足节点数量；
- 每个场景可追溯到已批准场景卡和事实标签；
- 人工走查覆盖所有继承级别和合法组合。

### 8.2 数据与兼容

- 2.1 不改变 schema4；2.2 起 v5 迁移幂等；
- 来源 v4 不被覆盖，3.0 回滚到 2.x 时旧键仍可读；
- 存档导入先内存验证，失败不覆盖目标槽；
- 第一季新游戏、31 个章节回放、关系回忆和既有结局全量回归；
- 同版本内容修订不会误触发 schema 迁移。

### 8.3 客户端与素材

- 类型检查、全部单元测试、内容图测试、构建、E2E 和资产审计通过；
- 375×812、430×932、844×390 和桌面均可完整游玩；

- 本版托管视觉 `pending = 0`。

### 8.4 发布证据

每版必须有独立 acceptance、release 和 rollback 文档，明确区分：

- 已自动验证；
- 已人工验证；
- 仅规划、尚未验证；
- 线上或公网已验证。

源码中的版本号不能单独作为“已经发布”的证据。

## 9. 内容变更控制

- 2.2 实现前，用户必须冻结第二季 canon：时间范围、事实标签、活跃路线、角色表、继承字段、失败状态和结局结构。
- 冻结后新增角色、路线、结构结局或公共事实属于范围变更，先回到 canon 决策，不在实现中顺手加入。
- 已发布 episode 只允许修错、补 alias/tombstone 和不改含义的文字修订。
- 大范围重写必须提升 `contentRevision`，提供旧节点落点和跨修订回归夹具。
- 没有后端或遥测时，平衡依据必须标为人工反馈或创作判断，不能伪装成用户数据结论。

## 10. 迁移、回滚与删除策略

- 2.0/2.1 回滚继续使用 v4；2.2 起每次部署都保留旧构建和旧数据键。
- 3.0 → 2.x 回滚时，2.x 看不到 v5 第二季进度是可接受妥协，但不得删除或覆盖它。
- 再次进入支持 v5 的版本时，原第二季进度必须恢复。
- 任何 schema、收藏或内容修订迁移都必须可重复执行，并对损坏数据给出隔离错误，不静默重置。
- 普通存档删除不得连带删除 outcome archive；归档删除必须独立确认影响。
- 3.0 范围内不删除 v4/v3/legacy 存档键；后续清理必须另立破坏性变更方案。

## 11. 兼容性妥协

- 第一季旧存档没有完整稳定选择日志，第二季只能继承可证明的结果摘要。
- 第一季旧 ID 保持原格式；只有补遗和第二季采用新前缀，因此命名不会完全统一。
- 2.2 的 v5 第二季历史从新季开始，不能在一个历史列表中无损重建第一季全过程。
- 回滚到只支持 v4 的客户端时，v5 进度暂时不可见，但数据保留。
- outcome archive 增加少量本地数据和导出体积，换取跨季来源不长期占用普通存档槽。
- 当前 32 项旧视觉可被明确延期，不阻断无关版本；这不等于把 fallback 认定为正式成品。

## 12. 有意不做

- 本轮不编写未经用户确认的第二季具体剧情、日期、角色行为、路线数或结局数。
- 不修改 Vue、TypeScript、剧情节点、存档、版本号或部署配置。
- 不生成、转换或接入图片。
- 不引入账号、云存档、遥测、数据库、付费或多人实时功能。
- 不用节点数量替代剧情质量，不为“平均”复制低价值场景。
- 不在 3.0 前删除第一季旧键或重写既有第一季事实。

## 13. 实施授权边界

本文和分版文档完成的是 Sol 方案。后续每个版本开始前，主 Agent仍需：

1. 核对前置版本的发布证据；
2. 对尚未冻结的 canon 决策请求用户确认；
3. 定义本次完成标准与明确非目标；
4. 把内容、代码、素材接入和验证拆成边界清晰的任务；
5. 在无独立 Git worktree 的当前项目中串行执行写任务；
6. 按分版验收标准逐项验收，不接受部分完成。
