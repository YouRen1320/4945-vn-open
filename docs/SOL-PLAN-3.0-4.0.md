# 《4945区》3.0 → 4.0 Sol 总方案

> 文档状态：Sol 条件规划完成；这是 3.0–4.0 的权威方案索引，不代表 3.0、第二季或第三季已经实现。
>
> 制定日期：2026-08-05。
>
> 现实基线：当前工作区仍是 `2.0.0` 本地实现候选；本方案只有在 2.0–3.0 路线真实完成并通过 3.0 acceptance 后才能进入实施。
>
> 事实边界：当前确认事实只到 2026-07-28；第三季日期、事件、主题、角色、路线与结局必须由用户另行冻结。
>
> 分工边界：Sol 负责规划、剧情合同、图片提示词与验收；图片由用户使用外部模型生成；本轮不修改运行时代码或素材。

## 0. 结论

3.0–4.0 延续“内容主导、逐集交付”，但不机械复制第二季方案：

- `3.0` 是完整第二季稳定版，也是第三季规划的证据起点，不追加剧情；
- `3.1` 用第二季回望补遗关闭经批准移入 3.x 的可选线索，同时建立不可变季结局档案；
- `3.2` 冻结第三季 canon，交付第三季共通序章，并从结局档案创建新的第三季进度；
- `3.3–3.9` 按时间切片覆盖全部第三季活跃路线，依次完成新目标、不可逆承诺、中点、关系重排、最终危机、主要结局和多季尾声；
- `4.0` 不再增加剧情，只把 3.2–3.9 已冻结的完整第三季晋升为稳定版。

最重要的架构变化不是再升一次存档 schema，而是让 schema5 从一开始就支持多季 campaign、不可变 `SeasonOutcomeRecord` 和版本化 `ContinuityProfile`。开始第三季不应要求玩家永久保留某个第二季普通存档槽，也不应把两季完整状态复制进第三季。

## 1. 规划前提与证据边界

本方案依赖的未来前提：

1. 2.2 已按规划启用 canonical schema5、收藏 v2 和稳定 choice ID；
2. 2.2–2.9 已逐集交付完整第二季；
3. 2.9 已关闭第二季主要 payoff，形成第二季结局摘要；
4. 3.0 已通过内容、迁移、离线、素材、公网和回滚验收；
5. 用户完成第二季复盘，并确认第三季是否立项。

这些前提目前都不是已实现事实。若 3.0 最终数据合同、内容规模或玩家反馈与规划不同，3.1 开始前必须更新本方案，不能拿过期假设直接实施。

## 2. 不能机械沿用上一阶段的原因

| 新问题 | 若不处理的后果 | 冻结处理 |
|---|---|---|
| 第二季来源与第三季目标都在 v5 普通槽 | 保留来源会长期占槽，覆盖来源又失去回顾证据 | 完成季生成独立、不可变的 outcome archive |
| 第一季结果 × 第二季结果 × 路线 × 伴侣继续相乘 | 场景、测试和素材组合不可控 | 第三季只消费归一化 continuity profile 与影响分级 |
| 每季都直接复制上一季 `GameState` | 临时 flags 和历史形成跨季隐式 API | 只继承版本化 outcome records，不携带运行态 |
| 为第三季惯性升级 schema6 | 无必要迁移和回滚成本 | schema5 按多季设计；只有不兼容数据变更才评审 schema6 |
| 三季图片全部自动离线缓存 | 浏览器配额、下载量和更新失败风险上升 | 用户选择季包，显示估算，不静默驱逐当前内容 |
| 旧角色/路线被要求永久结构性延续 | 叙事债务无限增长 | continuity debt ledger 明确延续、降级、退休和关闭 |
| 3.1 再次重复 2.9 尾声 | 填充内容、没有新价值 | 只处理 postmortem 发现的视角缺口和获批 3.x 线索 |
| 4.0 被当成“最后补剧情”的缓冲区 | 冻结失效，RC 无法稳定 | 3.9 内容完整；4.0 只晋升与发布 |
| 第三季新玩家必须先玩两季 | 进入门槛过高 | 提供有剧透提示的引导式连续性建档，不静默指定 canon |
| 生成图缺少跨季来源记录 | 角色外观漂移且难以复现 | 每季角色锚点版本化，并记录外部生成 provenance |

## 3. 产品路线方案比较

### 3.1 可行方案

#### 方案 A：3.x 只做功能与补遗，4.0 一次性交付第三季

初期改动少，但会重现第二季旧方案的内容爆量、素材积压和晚期测试风险。

#### 方案 B：3.1 桥接，3.2–3.9 逐集第三季，4.0 稳定晋升

每版交付完整剧情单元；架构、存档、素材与故事同步演进。

#### 方案 C：第三季建立独立应用

隔离最彻底，但会重复引擎、设置、收藏、可访问性和部署能力，跨季体验割裂。

### 3.2 决策维度

| 维度 | A 4.0 大爆发 | B 逐集第三季 | C 独立应用 |
|---|---|---|---|
| 实现成本 | 前低后高 | 中，持续可控 | 高 |
| 迁移成本 | 高，问题集中到末期 | 中，逐版验证 | 高，跨应用传递 |
| 风险 | 高 | 中低 | 中高 |
| 回滚难度 | 高 | 低到中 | 应用回滚低，数据协同高 |
| 长期维护 | 低 | 高 | 中低 |

推荐方案 B。它保持一个客户端和一套引擎，同时避免把完整第三季压到 4.0。

## 4. 跨版本剧情合同

### 4.1 完整剧情单元

除 3.0 起点和 4.0 晋升外，3.1–3.9 每版必须具备：

1. 明确的时间窗口与局部问题；
2. 共通主干或完整补遗框架；
3. 本版本要求覆盖的全部活跃路线/结局族；
4. 人物、成员或关系拍点；
5. 至少一个有即时后果的有效选择；
6. 延迟后果的目标版本与 fallback；
7. 对局部问题的阶段收束；
8. 图片提示词、素材清单、内容图和人工走查脚本。

3.1 补遗不允许复述 2.9 尾声；3.2–3.9 不允许只发布技术壳、预告或不可操作的“待续”节点。

### 4.2 第三季 canon

3.2 实现前必须由用户确认：

- 第三季时间范围与结束边界；
- 公共事实、改编事实和架空事实；
- 第三季主题命题与公共主冲突；
- 活跃、退休、回归和新增路线；
- 可使用、缺席、回归和新增角色；
- 第一、第二季 outcome fields 的继承级别；
- 失败状态、主要结局与关系收束结构；
- 哪些旧线索必须回收、只作 flavor 或正式退休。

本方案只定义戏剧功能，不猜测任何具体答案。

### 4.3 路线延续与退休

第三季不承诺把前两季每条路线永久保留为结构路线。每个旧结果必须被分类：

- `active`：第三季继续作为可玩结构路线；
- `acknowledged`：通过 scene/flavor 承认，但不形成独立结构；
- `retired`：经用户批准完成退出，并有不突兀的连续性说明；
- `unavailable`：事实或创作边界禁止使用，必须有安全 fallback。

退休不是删除旧内容。旧 ID、结局档案和回放继续保留；第三季只是不继续承担无限分支债务。

### 4.4 连续性债务总账

3.1 建立 `ContinuityDebtLedger`：

```text
threadId
originSeason
originRelease
factClass
currentStatus
requiredPayoff
targetRelease
routeScope
relationshipScope
retirementPolicy
fallback
testIds
```

第二季 `moved-to-3.x` 项必须在 3.1 被关闭、正式提升为第三季线索或退休。不得把“以后可能用”无限延期。

### 4.5 ID 与修订

- 第二季回望补遗使用 `s2x-`，提示词使用 `S2X-`；
- 第三季节点、选择、结局和素材引用使用 `s3-`，提示词使用 `S3-`；
- 现有第一季 ID、`s1x-`、`s2-`、`s2x-` 与新 `s3-` ID 只追加、不复用、不改义；
- 结构修正保留 alias/tombstone；
- `schemaVersion`、`contentRevision`、`profileVersion` 和 `outcomeRecordVersion` 分开演进。

## 6. 多季连续性架构

### 6.1 不可变季结局记录

完成一季时生成 `SeasonOutcomeRecord`：

```text
outcomeId
outcomeRecordVersion
lineageId
parentOutcomeIds
seasonId
contentRevision
source
endingId
relationshipResolutionId
durableFacts
payloadDigest
createdAt
supersedesOutcomeId?
```

`parentOutcomeIds` 精确记录本季从哪些上一季结果派生；第一季记录为空。记录只包含后续季允许消费的结果，不包含完整 `GameState`、历史、processedNodes 或任意 flags。创建后不可就地修改；事实修正创建带 `supersedesOutcomeId` 的新记录，并保留旧证据。

结局记录存入独立版本化命名空间，例如：

```text
4945-vn:v1:outcomes
```

删除普通存档不删除 outcome record。删除结局档案必须是独立操作，展示会影响哪些后续 campaign，并要求明确确认。

### 6.2 连续性档案

第三季只读取 `ContinuityProfile`：

```text
profileVersion
lineageId
outcomes: [season1Record, season2Record]
normalizedFacts
activeRelationshipClass
retiredThreads
createdAt
```

`normalizedFacts` 是第三季 canon 批准的最小白名单。它不等于把两个 outcome payload 简单合并；冲突、缺失和退休规则在领域层确定处理。

每个第三季 campaign 保存连续性档案的值快照，并记录来源 outcome IDs。后来删除或 supersede 来源记录，不静默改写已经开始的 campaign。

### 6.3 第三季开局

```text
标题页“第三季”
  -> 选择已完成的第二季 outcome record
     或进入有剧透提示的引导式连续性建档
  -> 查看第一季 + 第二季人类可读摘要
  -> 选择第三季目标槽
  -> 创建新的 season3 campaign
  -> 游玩 3.2 共通序章
```

不自动选择最近存档或所谓“官方结局”。引导式建档只询问第三季实际消费的维度，并限制为 canon 合法组合；它生成 `source = recap` 的合成 outcome records，明确标记并与实际通关记录区分。

### 6.4 campaign、槽位与导入导出

- schema5 从 2.2 起预留稳定 `campaignId` 和 `lineageId`；
- outcome archive 独立于 auto/quick/六个手动槽，解决跨季来源长期占槽；
- 创建第三季目标档不覆盖第二季来源 outcome；
- 覆盖已有第三季目标槽需要单独确认；
- 导出 campaign 必须携带其 continuity profile 快照和依赖的 outcome records；
- 导入先验证版本、digest、ID 冲突和合法组合，再写目标槽；
- 重复导入同一 outcome 不复制，冲突记录隔离并保留证据。

### 6.5 schema 政策

3.x 默认继续使用 schema5。新增 season3 内容、outcome record 版本或 profile 版本不自动意味着 schema6。只有 `GameState` 或 `SaveRecord` 出现无法向后兼容的结构变化时，才按重大变更另行比较 schema5 扩展与 schema6 迁移。

4.0 的 major 版本表示完整第三季产品里程碑，不表示故意破坏旧存档兼容。

## 7. 组合规模控制

### 7.1 两层输入

第三季剧情只接受：

1. 当前第三季 route/episode state；
2. `ContinuityProfile.normalizedFacts`。

不得直接读取第一季或第二季原始存档。每个 normalized fact 声明 flavor、scene、structural 或 ending 最高影响级别。

### 7.2 覆盖策略

- structural/ending 等价类必须穷举自动路径；
- scene 类必须覆盖每个合法场景族；
- flavor 类使用代表组合、快照与 fallback 测试，不做无价值笛卡尔积；
- 每个 episode 维护组合预算，新增结构维度必须删除、合流或退休等量债务；
- 任何合法 profile 都必须命中完整路径，不允许依赖隐藏默认路线或伴侣。

### 7.3 新玩家 fallback

引导式建档不是任意 flags 编辑器。它由 canon 提供少量人类可理解的合法 continuity bundles；所有 bundle 都必须能从 3.2 走到合法结局，并在 UI 中明确其剧透范围和非历史复原性质。

## 8. 离线与容量合同

三季资源不再默认全部缓存。离线管理至少支持：

- 按季显示预计下载体积、已缓存版本和完整性；
- 玩家显式选择下载/更新/删除某季资源包；
- 当前正在游玩的 episode 与共享 UI 资源优先保护；
- 配额不足时先提示需要空间，不静默删除其他季；
- 删除资源包不删除存档、outcome archive、收藏或设置；
- 离线启动只承诺已完整下载的季和 episode；
- 更新采用完整包切换，不能留下新旧节点与图片混用的半包。

4.0 最终验收不要求设备同时缓存三季全部图片，但要求任一单季包可独立完整下载、验证、游玩和删除。

## 9. 素材与提示词合同

### 9.1 编号与版本归属

- 3.1 补遗提示词：`S2X-*`；
- 3.2–3.9 第三季提示词：`S3-*`；
- 每版独立 manifest、prompt pack 和 acceptance；
- 每项必须拥有 `targetRelease`、状态、fallback 与人工验收。

### 9.2 角色连续性

第三季使用版本化角色锚点，不默认复用第二季外观：

```text
characterId
anchorVersion
seasonId
confirmedAppearanceFacts
allowedChanges
forbiddenDrift
referenceAssets
```

外观变化只有在 canon 确认后才能写进提示词。

### 9.3 外部生成 provenance

用户提供图片时，manifest 记录可获得的外部模型名、提示词版本、参考图、生成日期、尺寸、后处理和人工验收结果。无法取得的参数标为 unknown，不猜测 seed 或模型版本。

稳定发布要求本版 `targetRelease` 的托管视觉全部 ready。低差异 flavor 文本不单独生成图片；视觉预算优先关键行动、转折、危机、高潮与尾声。

## 10. 每版验收

### 10.1 内容

- 本集局部问题得到解决，全部活跃路线/结局族可完成；
- 场景可追溯到 canon、场景卡和事实标签；
- 选择有即时后果，延迟后果进入 S3 payoff ledger；
- continuity debt 到期项被回收、批准关闭或正式退休；
- 无死节点、伪结局、跨季普通跳转或未发布内容依赖。

### 10.2 连续性与数据

- 所有合法 outcome/profile 类别有路径或明确 fallback；
- outcome archive 创建、去重、supersede、删除影响和导入导出通过；
- 普通存档删除不影响已归档季结果；
- 从 3.0 和每个已发布 3.x 版本升级、回滚、再升级均保留数据；
- 第一季、第二季、补遗、回放和旧收藏全量回归。

### 10.3 客户端、离线与素材

- 类型检查、全部单测、内容图、构建、E2E 与资产审计通过；
- 375×812、430×932、844×390 和桌面流程完整；
- 键盘、焦点、读屏、低动态、长文本与剧透提示通过；
- 单季离线包下载、更新、删除、配额不足与回滚通过；
- 本版托管视觉 pending 为零，生成图完成人工验收。

### 10.4 发布证据

每版独立记录自动、人工、离线、预发布和公网验证。源码版本、计划文档或 release note 都不能单独证明已发布。

## 11. 迁移与回滚

- 3.x 与 4.0 保留 v4、v5、旧收藏和 outcome archive 旧版本；
- 回滚到较早 3.x 时，未知后续 episode 显示需升级并保留原数据；
- 回滚到 3.0 时，第三季 campaign 暂时不可见，但第二季与 outcome archive 保留；
- 再升级后第三季进度恢复；
- outcome record 修正使用 supersede，不原地改写玩家已开始 campaign 的连续性快照；
- 4.0 范围内不删除任何旧季数据键，清理另立破坏性方案。

## 12. 兼容性妥协

- 第三季不会结构性延续前两季每条路线；部分旧结果只获 flavor/scene 承认或正式退休。
- 回滚到不了解第三季的版本时，第三季进度暂时不可见但不会删除。
- outcome archive 与 continuity profile 会增加本地数据和导出包体积，换取来源档不占槽与可追溯性。
- 旧第一季选择仍无法精确复原；多季连续性只继承可证明结果。
- 为控制组合规模，flavor 变体不做全笛卡尔积自动路径。
- 离线体验改为按季选择下载，不再默认三季全部可离线。

## 13. 有意不做

- 不编写未经确认的第三季具体日期、事件、角色行为、路线数或结局数。
- 不假设 4.0 是整个作品的最终完结，只定义第三季完整里程碑。
- 不因版本号进入 4.0 就自动升级 schema6。
- 不把完整第一季/第二季 `GameState` 带入第三季。
- 不做账号、云存档、遥测、数据库、付费或多人实时功能。
- 不生成、转换或接入图片，不替用户选择外部模型。
- 不修改运行时代码、存档、版本号、部署配置或当前剧情节点。

## 14. 与 2.0–3.0 方案的交接

为了让本方案可实施，2.0–3.0 方案需要补充三项前向兼容要求：

1. schema5 从 2.2 起包含 `campaignId`、`lineageId` 和版本化 continuity/outcome 基础合同；
2. 2.9 完成第二季时生成不可变 `Season2OutcomeRecord`；
3. 3.0 acceptance 验证 outcome archive 的持久化、导入导出、删除隔离和回滚。

这些只是规划合同同步，不代表本轮实现数据模型。若后续选择不同架构，必须在 2.2 实现前重新进行成本、迁移、风险、回滚和长期维护比较。
